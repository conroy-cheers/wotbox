# Wotbox application architecture

## Implementation status

Pack acceptance commits the decision, queued work, capacity reservations and change event together. Capacity checks use the client's latest available free-space sample and outstanding pack reservations. A failed capacity lookup leaves the reservation durable for subsequent checks. Download workers preserve staged torrent bytes and freeze the configured client endpoint. Unverifiable historical destinations and ambiguous token effects enter review. Replacement decisions continue to use the source tracker and the exact proposed variant.

Each qBittorrent observer stages full membership in batches and publishes the changed links, absence decisions, generation and change event in one SQLite commit. The observer acknowledges the RID after commit. The final write transaction grows with the number of changed links and affected jobs. The projected Library stages full rebuilds before activation and processes dirty admissions in bounded batches. SQLite filters and pages the artist index, mixed search results and the releases on artist detail. The existing artist detail response also includes the complete nested catalog for compatibility.

Workflow writes and governed provider dispatch check the current lease using a unique token for each claim. Channel and release refreshes run through the durable queue. Explicit import intents can share one physical target while retaining separate obligations. Target scan acknowledgement, source removal and source refresh have distinct durable records. The current qBittorrent adapter supports torrent-only removal and blocks automated payload deletion because it cannot coordinate every writer on the storage.

Versioned read endpoints return a change-feed cursor from the same SQLite snapshot as the response. The frontend uses those revisions to reconcile progress and removals after replay or reset. Artwork has immutable versioned URLs and recoverable tombstones, with revalidating aliases for existing URLs.

The migration fixture exercises SQLite schema rollback, a populated upgrade and restart recovery. Production migration rehearsal and host performance measurements remain pending. Automated file deletion on exclusively managed storage requires a coordinated storage adapter.

The remaining sections record the design and rollout acceptance criteria.

## Operating model

Keep the single process, exclusive instance lock, embedded UI, SQLite WAL, provider governor, canonical catalog, and durable worker lanes. Tracker data determines source identity and download economics. qBittorrent determines which torrents are present and their transfer state. SQLite records the user's decisions, observed facts with their age, and work owed. Plex acknowledges refresh requests. Each authority has a different clock. A successful SQLite commit can authorize an external effect, but it cannot establish that the effect happened.

A command records the domain transition, dependent jobs, and durable change event in one short SQLite write transaction. A worker claims the next step, performs external I/O outside the transaction, and commits the result conditionally on its lease and the expected workflow version. A reader uses a versioned projection. HTTP handlers translate inputs and outputs. They do not coordinate workflows. A database write failure leaves the command retryable with the same identity.

| Owner | Responsibilities and entry points | Durable records |
|---|---|---|
| Acquisition | Decide or replan a pack, submit a specific variant, snapshot user policy and destination | Packs, decisions, item outcomes, download jobs, submission attempts |
| Client synchronization | One supervised poller per configured client, normalized inventory, presence and progress observations | Client snapshot generation, links, download events, reconciliation batches |
| Imports | Adopt observations, bind planned targets, authorize and reconcile supersessions | Logical imports, job associations, source cleanup steps, Plex obligations |
| Work scheduling | Claim, defer, renew, cancel, recover, and finish typed work | Existing background jobs with claim generation, next step and provider |
| Provider governor | Admit an individual outbound call under the configured class, limits, circuit and queue | Existing provider state and restart-sensitive quota windows |
| Library and artwork | Track dirty dependencies, publish a queryable library, own blob lifecycle | Dirty keys, admissions, projections, status revisions, assets and blobs |
| Change feed and UI | Replay committed changes, invalidate affected queries, reconcile ephemeral progress | Change log, database instance epoch, client-side cursor and overlay |

In Rust, introduce application modules at these boundaries as their operations move. Express keys as distinct types: VariantKey(tracker, torrent_id), ClientTorrentKey(client, lowercase_info_hash), ReleaseId, ImportId, and DownloadJobId. Keep existing API DTOs at the edges. A repository method performing part of a command accepts the caller's transaction. Only the outer command commits. Workers depend on these application interfaces. The composition root wires HTTP, workers, observers, and adapters. A supervisor owns task cancellation and joins, including the channel scheduler. Shutdown stops new claims and polls, drains bounded in-flight operations and leaves unfinished durable steps recoverable.

### Persistence contracts

| Logical record | Required key | Durable contents |
|---|---|---|
| Decision receipt | Unique pack ID, result per pack and ordinal | Request digest, winning version, resolved selection, immutable result and job references |
| Submission attempt | Job ID and attempt number, separate unique request keys | Frozen client instance, destination, token decision, stage checksum and effect state |
| Observation batch | Client instance, generation and sequence | Requested and returned RID, validated membership or changed hashes, application watermark |
| Physical import target | Unique client instance and hash | Shared observed facts. Separate intent IDs hold job associations, accepted policy and historical baseline |
| Source obligation | Intent, source client and hash; unique active removal claim per physical source | Verification generation, authorized mode, original source root, effect receipt and post-delete scan reference |
| External effect | Workflow, step, subject and attempt generation | Normalized arguments or digest, dispatch intent, outcome and reconciliation evidence |
| Projection and change feed | Generation and entity key; event sequence within epoch | Dirty version, acknowledged version, transaction revision and affected resources |

Use foreign keys for intent, target, job and scan associations. Keep terminal effect identities and decision receipts for the lifetime of the parent workflow, independently of background-job history pruning. Replacing an endpoint under the same configured client name requires confirming or changing its instance identity before resuming effects. Each adapter operation declares whether it is a read, a repeatable effect, or an effect requiring outcome reconciliation.

## 1. Pack decisions and submission

**Decision contract.** Accept receives pack ID, expected plan version, and optional selected ordinals. Resolve an omitted selection to the executable set in that plan. Reject has the same version precondition. Record a canonical request fingerprint, the resolved selection, and the result including job IDs under a unique pack decision. Replays of the identical command return that result, including after a lost HTTP response. A different selection or decision after commitment returns 409. For omitted selections, compare the original request form on replay before recomputing anything. Existing clients retain the current paths and response fields.

1. Build any expensive preview outside the write transaction. Capture the versions of preferences and the facts that affect eligibility, holdings, capacity and token budgeting. A projection watermark alone is insufficient if its dirty queue is behind.
2. Under BEGIN IMMEDIATE check the pack is open, plan version/fingerprint match, and relevant input versions are current. Revalidate local predicates and reserve shared budget or capacity in the same transaction where that policy limits concurrent submissions. If inputs changed, return the existing stale-plan conflict. Replan and manual resolution use the same open/version guard and increment the version.
3. Store accepted and excluded ordinals, reusable or new download jobs, import tasks, supersession sources, work items, reservations and the event. Reject writes only the decision and event. Persist the cleanup mode actually accepted. For trumped items use the source tracker and the exact proposed replacement variant when checking holdings. A different owned edition does not fulfill the replacement. A replacement already present may still require an import with zero download jobs.
4. Commit, then wake workers. A lost wake is harmless because claims poll durable work. The HTTP response describes accepted work; submission failure remains visible independently. Release reservations on cancellation or definitive failure and reconcile them against authoritative account information after an ambiguous charge.

**Submission identity.** Bind a job to the accepted tracker, torrent ID, token decision, profile and resolved client/destination. Preserve the existing deduplication semantics for a live submission. Keep request keys and payload fingerprints in an association table so two callers can reuse one job and conflicting reuse of a request key is rejected. A retry of a terminal failure creates a numbered attempt. A profile edit cannot silently redirect an accepted attempt.

**Recovery steps.** Resolve metadata and policy → check client by known hash → record fetch intent → acquire and stage torrent bytes → bind verified hash → add to client → confirm by hash. A staged payload short-circuits any tracker file request. Write the private stage under the job/attempt identity with restricted permissions, fsync the file, rename atomically and sync the containing directory. Validate the torrent hash against known metadata and retain its checksum. Do this immediately when bytes arrive, before unrelated metadata or inventory writes. On restart discover and verify the deterministic stage even if its database acknowledgement was interrupted. Remove it only after a durable terminal result; run an idempotent orphan sweep after recovery.

A token-bearing fetch crosses a billing boundary. Persist its intent **before dispatch**. If recovery finds intent with neither a valid stage nor authoritative evidence that retry is safe, mark the attempt as requiring review. Expose the reason and an explicit retry carrying the token choice. An ambiguous upstream outcome cannot be made exactly-once locally. For an ambiguous client add, query the frozen client by hash, and resume from the stage if absent; retry according to the adapter's duplicate-add semantics. Cancellation after dispatch must reconcile the outcome. It cannot undo a tracker charge or assume a client add failed.

## 2. Observation, identity and bounded reconciliation

Each client owns its own backoff, next poll, full-scan deadline, governor attribution, merge cache and pending delta. Give each actor one outstanding request. Provider deferral schedules its next eligible time. Transport failure backs off only that client. Successful contact and successful local application have separate timestamps. Time-based full scans run independently of the number of polls.

**Delta protocol.** The adapter decodes and validates into a candidate cache and a batch tagged with the serving client's generation and requested/returned RID. qBittorrent patches may omit fields, so the committed cache and RID always advance together. Apply a small batch in a transaction, keyed by client/generation/batch, then acknowledge the candidate. Keep a failed batch in memory for replay. On process restart, sequence discontinuity or undecodable patch, discard the volatile base and request a full snapshot. A RID alone cannot reconstruct a patch base. During startup expose the age of the last complete observation.

**Full snapshots.** For a large response, normalize into generation-scoped staging rows in bounded transactions. Only a validated, completely staged generation can become current. Publish current generation via an atomic pointer swap. Compute a durable change set against the prior generation, including a SQL anti-join over that client's previously present hashes and active jobs with known hashes. Jobs missing from a complete snapshot become Unknown with a reason; an incomplete scan cannot infer absence. Preserve historical Library membership and missing-since for completed holdings. Do not mark unsubmitted jobs with no confirmed client presence missing merely because the hash has been calculated. Reconcile pending submissions through their own worker. Apply changed keys to dependent projections in resumable pages with a generation watermark. Serialize subsequent deltas behind that client's reconciliation or persist them in order. Emit a final reconciled inventory watermark when catch-up finishes. Discard abandoned staging generations after restart.

**Delta cost.** Index jobs by resolved client/hash and observations by client/hash. Compare normalized old/new fields once. Progress-only updates touch matching transfer rows and publish coalescible progress; an inventory, completion, linkage, or presence transition also dirties the relevant import/library/pack keys. Preserve the original completion timestamp and update business timestamps only when their meaning changes. No per-poll historical job scan or whole-table import sync. Keep separate bounded repair entry points with persistent keyset cursors.

**Adopting a target.** Use one transactional bind-or-adopt command for both observation and submission. Keep one canonical import per attached client/hash. Preserve unique job associations; several authorized requests may refer to the same physical torrent. If an explicit import and an observation-only baseline coexist, keep the explicit import ID, transfer observational history and job references, repoint pending work and retain an alias for the historical ID before freeing the duplicate key. If two explicit intents collide, preserve both authorizations and their source obligations; associate them with the same target and serialize any overlapping cleanup. Never inherit permission to delete from baseline history. A conflict over policy, source ownership, or destination becomes a reviewable conflict. Binding and enqueueing the next step share the same commit.

## 3. Replacement cleanup and Plex

Store progress per **source** under the accepted import, with source and target identity, original cleanup policy, resolved client instance, source path/root, scan target, verification time, and an operation generation. A unique active obligation per physical source prevents concurrent removal under competing imports. Existing API import states summarize these steps. The UI can display the blocking client, source and reason.

| Durable step | Successful transition | Recovery |
|---|---|---|
| Await target | Confirm the exact target on its client and completion, then select the accepted policy | Resume on target observation or bounded poll. A missing or retired client exposes a blocked reason |
| Keep | Record source retained and finish its obligation | Idempotent, including an already retained source |
| Verify cleanup | Verify same-tracker unregistered evidence, target presence, allowlisted roots, path ownership and source identity. Record source and target Plex scan targets | Refresh evidence after deferral, client configuration change, or lease loss |
| Request target scan | Persist an idempotent Plex work item and await successful request acknowledgement | Retry the same obligation. HTTP success establishes scan acceptance only. If product policy requires actual visibility before deletion, require a positive lookup of the replacement in Plex before advancing; absent proof retains the source |
| Remove source | Recheck volatile guards and commit a deletion intent with the exact source hash, client and allowed mode. Dispatch under the current claim | On ambiguous response check presence. Absence settles removal. If still present, verify identity, path and authorization again before any retry |
| Notify source root | In one commit settle source removal and enqueue a refresh for its recorded section/root | Applies equally to confirmed deletion and a previously dispatched delete now observed absent. Repeated scan requests are safe |
| Finish | Once each required scan is acknowledged and all sources settled, complete the import and update source states together | A pending or failed scan remains visible and retryable independently of torrent presence |

Use separate step identities for target and source scans. A debounced Plex job may satisfy several obligations only if its dispatch follows each triggering change. A scan already running when deletion occurs cannot fulfill the post-deletion obligation. If the source was absent before a path was ever recorded, settle its presence without inventing a path; record the unresolved scan target or queue a conservative refresh of the known applicable configured roots.

**Provider pacing.** Let verification steps wait asynchronously for grant using a cancellable, bounded, low-priority admission mode. Keep interactive precedence and all existing request intervals. For long waits, persist the next step, release the worker and resume there. Short-lived evidence has an explicit validity window; a partial verification pass alone cannot authorize deletion. Rechecks must themselves be able to progress at the configured provider spacing. No open SQLite transaction spans this work.

**File ownership.** Build an inventory across every client that can access the affected storage. Use a complete validated sync snapshot and its change stream, or paginate to exhaustion with stable ordering and verify that inventory did not change across enumeration. Treat an unstable offset traversal, unreachable client, missing path, or ambiguous mount mapping as incomplete. Map client paths to a common storage identity and normalized path components; verify file extents/paths for overlapping layouts where available. A string comparison across two independently mounted clients cannot prove disjointness. Reuse this index across the batch and revalidate source identity, target and relevant generations immediately before each dispatch. Ignore only the exact source being removed. Missing evidence blocks file deletion and leaves the accepted policy visible for an explicit change.

There is a final race when external writers can place new files or add another torrent between verification and qBittorrent's delete-files request. For a hard shared-file preservation guarantee, enable automated file deletion only on storage with enforceable exclusive/coordinated mutation ownership covering all writers. On ordinary shared storage, support torrent-only removal as an explicit policy and retain payloads for manual cleanup. A Wotbox mutex cannot provide this guarantee for independently operated clients. This restriction and the choice of Plex visibility policy should be visible when configuring destructive cleanup. Proposed default for delete-files is positive Plex visibility plus enforceable ownership; ordinary scan notifications continue to require only acknowledgement.

## 4. Scheduling and external effects

Use the existing background_jobs table for executable work. Add claim_generation and typed, versioned payloads; store domain progress in its owner tables. In a short write transaction select a runnable job by lane, next-run time, priority and stable age, applying provider and running-claim predicates **before** taking the first row. Use indexes for ready state/lane/time and active provider claims. Paused or blocked providers park dependent steps until resume; cooldowns use a wake time. Work with no provider remains eligible. Split multi-provider operations into steps so the claim refers to the provider actually needed next. Keep the governor authoritative at dispatch because foreground calls can change eligibility after claim. Measure the query plan with a skewed backlog; add a ready-provider index or per-provider heads if the database still scans a large blocked prefix.

Increment claim_generation at each successful claim. Heartbeat, step transitions, terminal errors, stage deletion and event emission must check that generation, workflow version and owner. An expired worker cannot publish a new outcome. Stop dispatching on uncertain lease ownership; an already dispatched network operation is recovered from its durable intent. Attempt limits apply to failed operations, while capacity deferrals preserve the attempt count. Backoff recurring maintenance after failure and expose the next run. Restore time-sensitive provider windows with their expiry and counts on restart where an upstream quota outlives the process.

Keep diagnostics by domain and step: oldest runnable job per lane/provider, claim/commit latency, lease expirations, age of pending client reconciliation, pending or ambiguous external effects, and last scan acknowledgement. Bound telemetry cardinality; keep per-hash detail on individual records.

## 5. Catalog, artwork and frontend reads

**Incremental library.** Record dirty release/artist IDs transactionally whenever a dependency changes, with a monotonically increasing version per key. Dependencies include held releases, canonical credits and sources, artist catalogs, artwork state and coverage/preferences. Maintain reverse indexes from affected artists, catalog keys and asset sources to their dependent releases. Fan out a broad preference or catalog update through a durable keyset cursor. Use these keys for admission as well as projection. Claim a bounded page, build derived rows, and clear only the dirty versions actually processed. If inputs changed while computing, leave the new version dirty. Advance the public revision with the rows it describes. Stage a full rebuild under a new generation; capture concurrent dirties and replay them before switching readers. Retain the previous generation until the switch is durable.

**Reads.** Store filter/sort keys and normalized artist memberships in the projection, with stable UUID tie-breakers. Push search, counts, order, limit and offset into indexed SQL, hydrate only the requested rows, and preserve existing artist/release totals and covered-Single rules. For mixed search keep both result sets and totals independently paged according to the existing contract. Return a bounded page for an artist catalog as an additive API where large catalogs need independent pagination. Keep legacy response shapes during transition. Maintain library-wide index status once, incrementally, including last successful client scan, coverage and queue counts. Expose it separately to new clients. Legacy composite responses read page and status in one database snapshot. Derive their ETag from endpoint/schema, normalized query, projection/catalog revision, artwork representation revision if relevant, and status revision. New page-only and status-only responses each validate their own dependencies. A status update alone must refresh an old composite client.

**Artwork.** Keep URL/source identity separate from blob content and encoder version. Maintain a blob row keyed by content hash and materializer version, source references, lifecycle state and deletion generation. Use immutable variant URLs containing content and encoder identity. Keep old source-based URLs as revalidating aliases. Compute and encode into private temporary files outside a transaction. Under a per-blob lock, install verified files atomically and commit the source-to-blob reference and ready state. Pruning takes the same lock, rechecks source references and age in its write transaction, tombstones an unowned blob, unlinks its files, then finalizes the tombstone. Hold the lock across filesystem publication/removal and its database acknowledgement. The exclusive process lock makes per-blob coordination sufficient within Wotbox. On restart finish tombstones, reconcile abandoned temporary files, and requeue a source if any required ready file is missing. Validate decoded dimensions and pixel budget before large allocations where the decoder supports header inspection; bound concurrent encoding memory independently of network slots.

**Live state.** Write a scoped change event with the domain commit. Use the post-commit watch channel only to wake replay. Give cursors a database epoch and monotonic event sequence. Retain bounded history and coalesce transient progress by client/hash. Persist domain transitions even when many progress updates collapse into one. A GET returns data and an as-of sequence from one SQLite snapshot. A newer overlay entry supersedes that response; a response at or beyond the entry's sequence retires it, including removal markers. On reset or epoch mismatch, cancel older in-flight requests, clear overlays and tombstones, fetch active snapshots and replay from their watermark. Buffer intervening events and apply only those newer than the corresponding snapshot. Reset again if history expires during recovery. Advance the cursor only after applying an event, namespace it by instance and base path, and bound overlay size with snapshot refresh on overflow. Declare resource dependencies alongside query definitions so a new page has an explicit invalidation contract.

**Variant navigation.** Generate release links carrying tracker and torrent ID, and preserve both in route parsing, focus, add dialogs, API requests, query keys and attachment lookup. Load an explicitly requested missing variant by its compound key and verify canonical release membership. Legacy ID-only links resolve automatically when unique. Multiple matches return the candidate trackers and prompt selection before a tracker-specific action. Preserve client/hash attachment links and reverse-proxy base paths.

## 6. Migration and delivery

1. **Add schema and observability.** Take a consistent SQLite backup together with the protected staging directory before migration. Add nullable identities, attempt/decision/obligation records, generation columns and indexes. Version the schema and queue payloads. Keep readers for existing jobs and API contracts. Prefer additive migrations and restartable keyset backfills with durable checkpoints. Reject an older binary against a schema with active new-format work.
2. **Switch acquisition and imports together.** With the instance lock held and workers stopped, inventory staged files, active jobs, hashes, explicit imports, supersessions, packs and historical decisions. Map current profile to client only when evidence agrees; ambiguous destinations require review. Preserve job and import IDs, terminal history, reservations derivable from accepted work, and retained/removed source states. An open pack with existing effects is a legacy partial decision: show existing effects, prevent automatic replay and require resolution of the remaining selection. An unknown historical token dispatch goes through ambiguity recovery. Never reauthorize cleanup from historical holdings or reconstruct an unrecorded user choice. Enable transactional decisions, bind-or-adopt, fenced execution and step recovery as a unit before resuming side effects.
3. **Switch client observation.** Start each client with a fresh full snapshot. Compare proposed and existing presence, job outcomes and library membership in read-only shadow projections. Investigate discrepancies before switching authority. Only one path writes active domain state or enqueues side effects. Disable the global import sweep after the keyed reconciler catches up; retain bounded repair.
4. **Switch catalog and UI.** Build new admission and read projections alongside the current generation. Compare IDs, counts, sort order, mixed search, artist memberships and status on a consistent snapshot, then switch readers atomically. Deploy additive ETag, cursor and route support before enabling the new frontend. Cut artwork serving and pruning over together after verifying references and files. Rebuildable projections may switch back while their prior generation remains current.
5. **Retire legacy orchestration.** Remove API-owned submission logic, detached scheduler ownership, duplicate import writers, broad scans and obsolete validators after their consumers switch. Recovery of authoritative decisions after rollout is forward migration or reconciliation from the committed effect ledger. A pre-upgrade database restore requires reconciling any later upstream charges, submissions and deletions before workers resume.

## 7. Acceptance gates

Use the normal HTTP handlers, real SQLite migrations, worker claim path, and governed adapter mocks for integration tests. Control clocks and inject faults immediately before and after each named commit or external acknowledgement. Run performance comparisons on an anonymized installation-sized fixture and a larger generated fixture. Numeric fixture sizes below are test inputs; establish latency targets from measured baselines on the intended host.

| Boundary | Scenario and required observation |
|---|---|
| Decision | Race accept/reject/replan and two incompatible selections. One decision wins; jobs, exclusions and source obligations exactly match it. Lose the HTTP response and replay. IDs and result are identical |
| Submission | Crash at fetch intent, after stage rename, after hash binding and after client add. A valid stage prevents another tracker fetch. An ambiguous paid fetch requires review. Reuse an idempotency key with different inputs and receive conflict |
| Observation | Delete a torrent while offline; interrupt full-snapshot staging; fail persistence after decoding a removal; fail one of two clients. A completed snapshot updates only the correct client, preserves library history and resolves missing active jobs. A failed client cannot delay the healthy one |
| Import identity and pacing | Exercise both observer/binder arrival orders, including two explicit intents. One physical target survives with all obligations. A same-client replacement completes through a governor enforcing 250 ms spacing even when mock responses are immediate |
| File cleanup | Put an overlapping torrent beyond row 100,000, omit a path, change the inventory mid-scan, or supply incompatible storage mappings. File deletion stays blocked. Test keep, torrent-only, and an exclusively managed delete-files case with independently verified target visibility |
| Plex recovery | Crash after dispatch, after deletion and after settling removal. Use distinct source and target roots. Every owed post-deletion scan remains recoverable, including when an earlier scan of that root was already running |
| Scheduling | Place 2,000 higher-priority cooling-down jobs ahead of eligible work. The next claim finds the runnable job. Expire its lease and deliver the former worker's result late; domain state and obligations reflect only the current generation |
| Catalog cost | At fixed page size and change cardinality, increase history tenfold. Compare rows read/written, statement counts, writer-lock duration, response size and p95 page latency. One progress update produces zero unrelated import updates; one admission batch has a bounded key count. Inspect query plans for paging and provider selection |
| HTTP and live state | Change scan status with identical projection rows and revalidate a legacy response. Remove and re-add a torrent across an expired cursor, then deliver an old GET late. New status and the re-added torrent both remain visible |
| Assets and routes | Interleave last-reference prune with same-content publication, restart between unlink and acknowledgement, and remove a ready file. References resolve or enter repair. Two trackers with the same numeric ID select distinct variants throughout navigation and submission |
| Upgrade | Rehearse migration twice on copies containing partial decisions, unknown token attempts, active leases, aliases and staged files. Compare counts and identities plus actual pending effects. Restart at each backfill checkpoint and verify bootstrap dispatches only authorized work |

Start implementation with the pack/submit/import transaction and recovery tests. They establish who can authorize work and what a retry may do. Client synchronization and queue changes can then use those contracts. Projection and UI changes can ship independently once the event and revision contracts exist.
